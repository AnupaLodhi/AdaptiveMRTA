# AdaptiveMRTA

### Obstacle-Aware Multi-Robot Task Allocation with Coordinated and Adaptive Reassignment

[![Python](https://img.shields.io/badge/Python-3.12-blue.svg)](https://www.python.org/)
[![Research](https://img.shields.io/badge/Project-Research-orange.svg)](#)
[![Reproducible](https://img.shields.io/badge/Experiments-Reproducible-brightgreen.svg)](#)

**AdaptiveMRTA** is a reproducible simulation framework for studying **Multi-Robot Task Allocation (MRTA)** in obstacle-constrained grid environments.

The project investigates how independent task-selection strategies compare with centralized path-cost assignment and how different reassignment policies behave when robots become unavailable during task execution.

The current framework includes deterministic scenario generation, A* path planning, coordinated Hungarian assignment, local and event-triggered reassignment strategies, robot-failure experiments, scalability studies, computational-work instrumentation, statistical analysis, and an interactive 3D visualization.

> **Research status:** Active research prototype. The repository contains completed simulation experiments and their raw/processed results. Scientific claims and terminology are being refined as part of the manuscript and literature review.

## Research Problem

Consider a set of robots

\[
R = \{r_1, r_2, \ldots, r_n\}
\]

and a set of tasks

\[
T = \{t_1, t_2, \ldots, t_m\}
\]

distributed in a two-dimensional environment containing obstacles.

The system must assign available robots to active tasks and navigate them through collision-aware paths while attempting to achieve efficient task completion.

The experiments study several practical questions:

- How much does coordinated assignment improve task completion compared with independent local task selection?
- How does obstacle density affect allocation performance?
- How does the system scale as the number of robots and tasks increases?
- How do allocation strategies behave when robots become unavailable during execution?
- Is global reassignment required at every simulation step?
- Can persistent assignments and selective reassignment reduce allocation work while maintaining successful task completion in the tested scenarios?

## Core Components

### Deterministic Scenario Generation

Experiments use seeded scenario generation so competing algorithms can be evaluated on matched environments.

A scenario contains:

- obstacle grid,
- robot starting positions,
- task positions,
- random seed,
- obstacle density, and
- a scenario fingerprint.

This allows paired comparisons using the same underlying scenario.

### A* Path Planning

Robots navigate the grid using A* shortest-path search with four-neighbor movement.

Path cost is also used by coordinated allocation methods when constructing robot-task assignment costs.

### Collision-Aware Simulation

The obstacle simulator incorporates:

- static obstacles,
- occupied-cell checks,
- movement reservations,
- blocked-movement tracking,
- task completion,
- unreachable-path tracking, and
- robot unavailability/failure events.

### Hungarian Path-Cost Assignment

The coordinated baseline constructs a robot-task cost matrix from A* path lengths and solves the one-to-one assignment using the Hungarian algorithm.

This explicitly coordinates task selection rather than allowing multiple robots to independently pursue the same task.

### Dynamic Reassignment

The repository contains several reassignment policies.

**Repeated global assignment** recomputes coordinated assignment throughout execution.

**Event-triggered global reassignment** retains assignments and performs global reassignment when stored assignments become invalid.

**Persistent local repair** preserves valid assignments and attempts to assign only currently unassigned robots and tasks.

The experimental **saturation-triggered local-to-global strategy** begins with persistent assignments/local repair but escalates to global reassignment when an active robot is unassigned while all remaining active tasks are already reserved.

This condition is treated as **reservation saturation**, not as a general proof of deadlock.

## Experimental Program

The repository contains a sequence of experiments developed to evaluate different aspects of the framework.

### E1 — Coordinated Assignment

Compares coordinated Hungarian path-cost allocation against independent Manhattan-distance and path-cost task-selection strategies.

Configuration:

```text
Robots:             15
Tasks:              20
Obstacle density:   20%
Seeds:              30
```

All evaluated methods completed all tasks in the tested scenarios.

The coordinated method substantially reduced total robot travel distance relative to the independent allocation baselines.

---

### E2 — Obstacle Density

Evaluates performance across:

```text
0%
5%
10%
15%
20%
```

obstacle density.

Each configuration is evaluated using matched scenarios across the competing algorithms.

The experiments examine task-completion iterations, travel distance, redundant targeting, blocked movement, and runtime.

---

### E3 — Scalability

Evaluates the framework using the following robot/task configurations:

```text
5 robots  / 10 tasks
10 robots / 10 tasks
15 robots / 20 tasks
20 robots / 20 tasks
20 robots / 30 tasks
30 robots / 30 tasks
```

Each configuration uses 30 seeded scenarios with 20% obstacle density.

These experiments evaluate empirical scaling within the tested range; they should not be interpreted as a theoretical complexity analysis.

---

### E4 — Dynamic Robot Unavailability

Robot-unavailability experiments evaluate:

```text
0%
20%
40%
60%
```

robot failure/unavailability rates.

Failures occur during simulation, after which affected robots are removed from active allocation and navigation.

These experiments represent **robot removal/unavailability**, not physical stranded robots remaining as new obstacles.

---

### E5A — Replanning Strategy Trade-Off

Compares:

- repeated global reassignment,
- event-triggered global reassignment, and
- persistent local repair.

The experiments show that persistent local repair alone can fail to complete tasks in a substantial fraction of the tested scenarios, while event-triggered global reassignment retains successful completion.

They also demonstrate that recomputing the full global assignment at every simulation step is unnecessary in the tested scenarios.

---

### E5B — Computational Work

Runtime alone is machine-dependent, so the framework also instruments deterministic allocation work.

Recorded counters include:

- assignment requests,
- global assignment calls,
- A* path-cost evaluations,
- successful path-cost evaluations, and
- unreachable path-cost evaluations.

In the E5B paired experiments, event-triggered global reassignment produced the same measured completion iterations and total travel distance as repeated global reassignment across all 60 tested paired scenarios while requiring fewer allocation-stage A* path-cost evaluations.

---

### E5C — Saturation-Triggered Reassignment

The final experimental comparison evaluates four strategies:

```text
Repeated Global
Event-Triggered Global
Persistent Local Repair
Saturation-Triggered Local-to-Global
```

across static scenarios and scenarios with 20% robot unavailability.

In the current 30-seed evaluation:

- repeated global assignment completed all tested scenarios,
- event-triggered global assignment completed all tested scenarios,
- persistent local repair failed to complete many scenarios within the simulation limit, and
- saturation-triggered reassignment restored successful completion across the tested scenarios while reducing allocation-stage A* evaluations relative to event-triggered global reassignment.

This reduction involves a trade-off: under robot unavailability, the saturation-triggered strategy required slightly more completion iterations on average than event-triggered global reassignment.

These results apply to the evaluated simulation configurations and should not be interpreted as universal performance guarantees.

## Evaluation Metrics

The framework records metrics including:

| Metric | Description |
|---|---|
| Success | Whether all tasks were completed within the simulation limit |
| Iterations | Simulation steps required for completion |
| Total Distance | Aggregate robot travel distance |
| Productive Robots | Robots contributing to task completion |
| Blocked Moves | Movement attempts prevented by occupancy/reservations |
| Redundant Targeting | Multiple robots independently targeting overlapping tasks |
| Runtime | Wall-clock execution time |
| Global Assignment Calls | Number of global assignment operations |
| A* Cost Evaluations | A* searches used to construct allocation cost matrices |

Runtime is reported as a secondary implementation-dependent measurement. Deterministic work counters provide a more reproducible measure of allocation computation within this implementation.

---

## Statistical Analysis

Experiments use paired scenarios so algorithms are compared under matched environmental conditions.

The analysis includes:

- paired differences,
- win/tie/loss counts,
- Wilcoxon signed-rank tests,
- percentile bootstrap confidence intervals, and
- rank-biserial effect sizes where applicable.

Statistical results should be interpreted together with effect sizes and observed performance differences rather than relying only on significance thresholds.

## Important Scope and Limitations

This repository represents a **simulation study**, not a physical-robot validation.

Current limitations include:

- static grid obstacles,
- fixed task locations,
- four-neighbor unit-cost movement,
- centralized coordinated assignment,
- scalability evaluation limited to the tested robot/task configurations,
- robot failures modeled as removal/unavailability,
- no dynamic task arrivals,
- no physical robot experiments, and
- machine-dependent runtime measurements.

The current implementation repeatedly uses A* to evaluate robot-task path costs. In static unit-cost grids, alternative preprocessing approaches such as distance fields or breadth-first shortest-path preprocessing could reduce this computational cost. Therefore, A* evaluation counts should be interpreted as computational work **within this implementation**, not as a general lower bound on MRTA computation.

The saturation-triggered strategy was developed after examining behavior in the same seed range used in the current E5C evaluation. Consequently, E5C should be treated as a development/in-sample evaluation rather than independent holdout validation. Evaluation on unseen scenario sets is future work.
